TrustMesh
Tagline:
"Secure Trust Infrastructure for Autonomous AI Agents."
Core product statement:
"AI can negotiate. TrustMesh makes sure it stays within authority. Blockchain makes the
commitment verifiable."
Core architectural principle:
REASON → ENFORCE → VERIFY
AI/Gemini = reasoning and negotiation
TrustMesh = identity, authorization, deterministic policy enforcement, and security
Blockchain = tamper-evident/verifiable commitment layer
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ 2. THE PROBLEM
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Autonomous AI agents are increasingly capable of acting on behalf of organizations.
In a future where agents from different companies interact directly, an organization needs to know:
Who is this agent?
Which organization does it represent?
•
•
•
•
•
1
Is its identity valid?
What is it authorized to do?
Which capabilities does it possess?
Is the requested action within its authority?
Does the action violate the transaction's constraints?
Can suspicious behavior be detected and blocked?
After two agents reach an agreement, can the agreement later be verified?
Traditional LLM-based agents can reason and act, but an LLM should not be treated as the final authority
for security-sensitive actions.
TrustMesh provides an infrastructure layer between autonomous agents that establishes:
Agent identity
Organization identity
Credentials
Capabilities
Authorization
Deterministic policy enforcement
Security monitoring
Verifiable agreements
Tamper-evident blockchain commitments
The key focus is cross-organizational agent trust.
Do NOT turn this into a generic chatbot security project or a generic AI firewall.

SECURITY PRINCIPLE ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
The LLM is NOT the security authority.
The LLM can:
understand intent
reason
generate offers
generate counter-offers
propose actions
generate structured decisions
But the LLM must NOT directly execute consequential sensitive actions.
The correct execution model is:
Intent ↓ AI reasoning ↓ Agent proposes action ↓ TrustMesh Gateway ↓ Identity verification ↓ Credential
verification ↓ Capability validation ↓ Authorization ↓ Deterministic Policy Engine ↓ Threat/security checks
↓ ALLOW / BLOCK ↓ Only if ALLOW → execute action ↓ Event emitted ↓ Audit trail
This separation must be clearly visible in both the architecture and the UI.
