1. Product Overview
1.1 Product Name

TrustMesh

1.2 Product Positioning

Secure Trust Infrastructure for Autonomous AI Agents

1.3 Core Statement

AI can negotiate. TrustMesh makes sure it stays within authority. Blockchain makes the commitment verifiable.

1.4 Core Architecture Principle
REASON → ENFORCE → VERIFY
REASON — AI Decision Layer

AI agents and Gemini:

understand intent
evaluate offers
generate proposals
negotiate
propose actions

AI is not authoritative.

ENFORCE — Deterministic Trust & Security Layer

TrustMesh:

verifies identity
verifies credentials
validates capabilities
checks authorization
evaluates deterministic policies
detects security threats
produces ALLOW / BLOCK decisions

TrustMesh is the security authority.

VERIFY — Cryptographic Verification Layer

TrustMesh:

freezes the final agreement
canonicalizes it using RFC 8785
generates a SHA-256 hash
commits the hash to an EVM blockchain

Blockchain is a tamper-evident verification layer, not the runtime security engine.

2. Problem Statement

Autonomous AI agents are increasingly capable of acting on behalf of organizations.

When an agent from Company A interacts with an agent from Company B, several trust questions arise:

Who is this agent?
Which organization does it represent?
Is its identity valid?
What capabilities does it possess?
What is it authorized to do?
Is the requested action within its authority?
Does the proposed transaction violate business/security constraints?
Can the final agreement be independently verified later?

Traditional agent systems primarily focus on whether an AI can reason and perform a task.

TrustMesh focuses on the missing layer:

Can autonomous agents interact with other organizations without being given uncontrolled authority?

3. Product Vision

TrustMesh provides a security gateway between autonomous agents belonging to different organizations.

The system allows agents to:

discover counterparties
verify identities
establish organizational trust
negotiate
propose actions
transact within predefined constraints

while ensuring that:

No consequential agent action can execute unless TrustMesh independently authorizes it.

The final agreement can then be cryptographically committed to a public blockchain for later verification.

4. Target Use Case
B2B Autonomous Procurement

A buyer organization delegates procurement to a Buyer Agent.

The Buyer Agent needs:

Product: packaging units
Quantity: 1,000
Maximum budget: $2,000

The Buyer Agent is allowed to:

It is NOT allowed to:

Supplier agents respond and negotiate through TrustMesh.

7. Core Security Principle
The AI is never the final authority.

Gemini may:

interpret intent
generate offers
generate counter-offers
suggest actions
provide reasoning

Gemini must NEVER:

approve its own action
directly execute consequential actions
access credentials
make final security decisions
bypass the Policy Engine

The architecture must enforce:

AI PROPOSES
      ↓
TRUSTMESH EVALUATES
      ↓
DETERMINISTIC DECISION
      ↓
ALLOW / BLOCK
      ↓
ONLY ALLOW → EXECUTE

There must be no direct execution path from AI to an agent runtime.

9. Identity and Organization Trust

Every registered agent belongs to an organization.

Example:

Buyer Agent
    ↓
Buyer Organization

Supplier B Agent
    ↓
Supplier B Organization

Identity verification must confirm:

agent exists
agent is registered
claimed organization matches registered organization
credential belongs to that agent
credential is active

An unknown or mismatched agent must be rejected.

10. Credentials

Credentials are synthetic credentials for the hackathon prototype.

Requirements:

credentials are issued to registered agents
credentials are bound to an organization
credentials can be active, expired, or revoked
raw credentials are never returned to the frontend
credentials are never stored in plaintext
HMAC-SHA256 may be used for stored credential digests
verification must use constant-time comparison

The blockchain must never contain credentials or credential hashes.

15. Deterministic Policy Engine

The Policy Engine is the final business/security enforcement layer.

It must not use an LLM to decide.

Example rules:

price <= maximum_budget
delivery_days <= maximum_delivery_days
quantity == requested_quantity
certification == required_certification
requested_capability is authorized
action is within intent

Every decision must return:

decision
rule_id
reason
evidence
evaluated_factors

Example:

decision: BLOCK
rule_id: BUDGET_LIMIT
reason: Proposed price exceeds authorized budget
evidence:
    proposed: 2500
    maximum: 2000

Money must be represented as integer cents, not floating point.

      ↓

24. RFC 8785 Canonicalization

The agreement must use RFC 8785 JSON Canonicalization Scheme (JCS) before hashing.

Requirements:

deterministic key ordering
deterministic number formatting
deterministic escaping
UTF-8 encoding
canonical JSON output

The canonical JSON must be stored off-chain.

The same agreement must always generate the same hash.

25. SHA-256

Use:

SHA-256

for the agreement hash.

Do not unnecessarily combine SHA-256 and Keccak for the agreement hash.

Keccak may be used where appropriate for blockchain references, but the agreement verification algorithm is:

RFC 8785 → UTF-8 → SHA-256
26. Blockchain

Blockchain is a verification/notary layer.

It must NOT:

approve actions
authorize agents
store credentials
store negotiation content
store sensitive organization data
control runtime security

It stores minimal commitment data.

Recommended fields:

agreementHash
transactionRef
buyerAgentRef
supplierAgentRef
committedAt

Agent references should be pseudonymous.

Resilience requirement:

A chain that is slow or wedged must never be able to take the console down.
/api/health, /api/overview and /api/blockchain/status all share one bounded probe, so a
node that accepts connections but never replies degrades those endpoints to a status
instead of holding the requests open. This is a hard requirement of §46, not an
optimisation.

Implementation note:

Every router is registered exactly once in app/api/routes/__init__.py and mounted in
app/main.py under settings.api_prefix (default "/api"). Route handlers declare paths
relative to that prefix (for example "/overview", not "/api/overview"); the prefix is
applied only in main.py. Adding "/api" inside a route decorator would produce a doubled
"/api/api/..." path and a 404 on every call.

Database access from async handlers goes through the single helper app.core.database.run_db,
which runs the callable on a worker thread and always closes the session in a finally
block. Routes must not construct a Session directly.

Product Hero

Data fetching note:

TanStack Query is NOT used. The console implements an equivalent, dependency-free layer in
frontend/src/hooks/useApi.js, exposing useApi / useMutation / useOverview / useTransactions
and so on. Each hook returns the four states the spec requires together — loading, empty,
error and disconnected — so a page cannot forget one. This was chosen deliberately to keep
the bundle small and the request lifecycle visible.

Build-time configuration (deployment-critical):

Vite inlines VITE_* variables at BUILD time, not at runtime.

VITE_API_URL must be set in the build environment whenever the API is hosted on a
different origin than the page (the normal production case: SPA on Vercel, API on Render).

If it is unset, the client falls back to location.origin and requests its own origin's
/api/... path, which a static host answers with the SPA fallback - every request fails and
the console renders empty. npm run build enforces this: the build fails with a clear
message unless VITE_API_URL is set or TRUSTMESH_SAME_ORIGIN=1 asserts that one host serves
both the page and the API.

VITE_API_TARGET is the local dev-server proxy target only and is ignored in production
builds.

Routing note:

The console uses HashRouter, so client-side routes such as /#/security resolve on any
static host with no rewrite rules.
